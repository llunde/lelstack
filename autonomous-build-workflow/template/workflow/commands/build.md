# build

Role: Orchestrator. Load the `caveman` skill. Read AGENTS.md, workflow/plans/index.md and workflow/questions/index.md. Don't read workflow/docs/ or source broadly. At session start, run workflow/commands/recover.md before the loop. Integrate each finished worktree unit with workflow/commands/integrate.md.

**Context hygiene.** You run longest, so keep your context small:
- Read indexes and notes by exact path, only the rows and sections the next step needs. Never read a whole folder.
- Take sub-agent returns as they come (≤ the stated lines). Never ask a sub-agent for its full output, and never paste logs; a Helper triages them.
- Don't re-read a file you have already acted on unless it changed.
- One status line per step (AGENTS.md §6 Voice).

**After a context compaction:** discard what the summary says about the state of the work. Finish nothing you "remember" being in the middle of. Re-run recover.md from disk, exactly as in a new session, then continue the loop.

**Session budget:** after a phase audit, or once you have closed the number of plans in harness.md (default 6) since your context was last reset, reset your context, since every turn re-reads all of it. Count closed plans from 0 at session start and after every reset or compaction (earlier ones are no longer in your context); don't re-derive the count from git. With automatic resume on, end the session cleanly (§4, "Session budget reached"). Otherwise, if the harness lets you compact or clear your own context (harness.md), do that and re-run recover.md. If it can't, carry on.

## 1. Dispatch rules
Pick tier and effort for every dispatch. Every dispatch costs quota or money, so start at the cheapest setting that fits the work and escalate only with a reason. The starting points below are defaults for your judgment, not fixed assignments.

**Ladder** (one rung up = the next step): fast / low → standard / medium → standard / high → strong / medium → strong / high. Effort is `low`, `medium` or `high`; harness.md maps these to the harness's own levels. Nothing above strong / high is used.

| Work | Start at | Start higher only when |
|---|---|---|
| Planner | strong / medium; standard / medium for small or pattern-following plans (sweep, reconcile, docs, a sibling of a done plan) | |
| Brief check | standard / medium | |
| Executor | standard / medium; fast / low for mechanical work with no logic (docs only, renames, deleting tests) | strong / medium: cross-cutting architectural change; subtle security, auth, concurrency or data-integrity logic |
| Reviewer, first pass | standard / medium | strong / medium: the plan is `review: full` (then no standard pass runs first) |
| Reviewer, deep pass | strong / high | only on escalation (§2 step 5) |
| Resolver | strong / medium | |
| Audit sections · synthesis, cross-cutting pass, final audit | section `light`: standard / medium, `full`: strong / medium · strong / medium | |
| Helper: failure triage, read-only gathering | fast / low | |

- **Briefs.** Every dispatch starts "Follow workflow/roles/<role>.md." followed by the inputs that role file lists under Brief, one `key: value` per line. Don't restate what the role file already says.
- **Units at the same time** only when all of these hold: their `owns:` paths are disjoint from each other and from every in-flight unit; none `depends_on` an unfinished plan; any shared contract they rely on has already landed; they belong to the current phase; the writing-unit cap in harness.md isn't exceeded.
- **Reason above the start.** A dispatch above its starting point names one concrete reason, from the table or the plan. "Important", "to be safe" or "best quality" are not reasons. Unsure: take the start; one failed cheap attempt costs less than routine expensive ones.
- **Model and effort:** the plan's `model:` is a proposal. Change it if needed; lower it when its stated reason doesn't hold.
- **Escalate on retry:** a fix round with a critical or high finding, an Executor sent back after verification, a re-dispatch after a contradiction, or `check` failing twice on one unit each go one rung up from the setting that failed. Skip a rung only with a stated reason. A retry never steps down. The ladder ends at strong / high: a retry that fails there becomes a remediation plan or a question, never a higher setting.
- **strong / high** only for a deep pass, or after strong / medium already failed on this unit. Size, importance, "to be safe" or a first attempt never count. Expect it rarely.
- **Usage running low** (only when the harness shows it; never guess): effort may drop on non-critical work, never on high-risk work. Prefer stopping and resuming to building high-risk code on a cheap setting.
- **Record** every dispatch's setting by role, with the one-line reason for any start above the table or any escalation: in "In flight" while it runs, and in the progress note's `Model:` line, which you complete at close (`Model: P strong/medium · B standard/medium · E standard/medium → standard/high (fix round: #1 open) · R standard/medium`).
- **Helpers read a lot and return little.** Never start an agent for something a quiet script already reduces to one line (a green `check`, a lint run). Start a Helper when a failure's output is more than a few lines, or when facts must be gathered across many files; several can run in parallel. Helpers return facts and evidence, never decisions: you decide.
- **Required integrations** (harness.md): in a phase that needs one, dispatch nothing until its tools are confirmed in this session: recover.md step 0 does this at session start, and when Pick moves into a phase that needs an integration not yet confirmed this session, run that check (recover.md step 0, Required integrations) before the phase's first dispatch; agents started before a reconnect may never get its tools. Every Executor brief in such a phase adds `integration: <name>`. On an `<integration> unavailable` return, or if it disappears from your own session, dispatch nothing new and stop (§4).
- **Stale rulebook:** if AGENTS.md or a workflow file changed during this session, add to every later brief: "Re-read AGENTS.md from disk; the copy loaded at session start may be stale."
- **Worktree briefs** (AGENTS.md §5). Every brief for work inside a worktree adds `main: <absolute path of the main checkout>` and gives workflow paths (plan, note, `out:`) as absolute paths under it.

## 2. Loop
1. **Pick.** The ready set is the Pri `next` rows, then the `planned` rows in the current phase in number order whose Deps are all done. If the current phase has no plan rows yet, first add one `planned` row per Scope-In bullet of its phase doc, in build order (as intake.md step 4). If the phase has none left (and nothing is in flight), go to §3. A phase can't start while an earlier phase has an acceptance row with `Blocking: yes` that hasn't passed. Take the first ready plan. While the parallel cap allows, also take further ready plans whose `owns:` is disjoint from everything already picked or in flight. A plan without a brief has no `owns:` yet, so plan it first, then decide. A fast-path plan (step 2) runs alone: don't pick it alongside other plans, and pick nothing alongside it. **When more than one plan runs at the same time, each runs as `parallel-worktree` units (the whole plan, or its slices if it has them), whatever its `execution`.**
2. **Plan.** For each picked plan without a file, dispatch a Planner (§1; workflow/roles/planner.md) with `row:` and the pointers you already hold, without extra reading. Several Planners can run at once, since each writes only its own plan file.
   **Fast path:** when the row's source shows the work will be `review: skip` (workflow/roles/planner.md: docs only, config only, or a text-only reconcile), skip the Planner. In step 3, dispatch one `sequential` Executor (§1) with `task: fast path`, `row:` and the `plan:` path to write. On a `not fast path` return, dispatch a Planner (§1) with `row:` and `complete: workflow/plans/NNN-slug.md`, then continue from the brief check.
   **Brief check** each picked plan that has no `## Brief check` section yet, unless it is `review: skip` or you run in single-agent mode (an agent checking its own brief finds little): dispatch a Reviewer (§1; workflow/roles/reviewer.md) with `task: brief check` and `plan:`. On blocking problems, dispatch a fresh Planner at the same setting once, with `revise: workflow/plans/NNN-slug.md`. No second check. If a plan's `## Brief check` lists a problem not yet marked `fixed` or `rejected` (a session died before the revision), dispatch only that revising Planner; never execute such a plan.
   Then turn the plan's proposed entries into real IDs (§5) and update the index rows (Exec, Deps).
3. **Execute** according to the plan's `execution`. Set the plan to `in-progress` in both the file and the index, add each dispatched unit to "In flight", and apply the plan's listed Hotspots. For worktree units only: before creating any worktree, save `chore(plan NNN): dispatch (plan NNN)` (AGENTS.md §6 Commits), so the Hotspots are in an app commit, because worktrees start from the integration branch HEAD.
   - **sequential:** dispatch one Executor (§1; workflow/roles/executor.md) at the plan's `model:` with `plan:`.
   - **parallel-worktree:** if the plan has Contract tasks, land them first: dispatch one Executor with `plan:` and `task: contract`, verify (step 4), review (step 5, `out:` the plan's progress note) and save. For each unit (a slice, or a whole plan picked alongside others), create its worktree from the integration branch HEAD (harness.md), run stack.md's worktree setup there, record the worktree and branch in "In flight", and dispatch an Executor into it with `plan:`, `main:`, `mode: worktree <path>, branch <b>` and, for a slice, `slice <X>`. With harness-native isolation, use `mode: worktree: harness-native` and record the path and branch the agent reports. Every later dispatch for the unit (resume, fix) passes `mode: worktree <path>, branch <b>` from "In flight", never `harness-native`, which would start a new worktree. Integrate each unit as it returns (integrate.md), one at a time.
4. **Verify.** For `sequential`, first apply the requested shared edits (worktree units: integrate.md step 3). Then run `check` yourself on the integration branch; if it fails with more than a few lines, start a Helper for failure triage (recover.md step 7) and pass its result to the Executor you send back. Read the reports and `git diff --stat`. Compare `git status` with `owns:` and name every file changed outside it, including files a tool or the app wrote, as `outside owns:` in any send-back and in the review brief; never discard them silently. Read the full diff only for load-bearing logic or files sensitive to constraints. Check every item in AGENTS.md §8. If something is missing, send a fresh Executor back once with `task: fix: <specifics>`, one rung up (§1), or fix a one-line gap with no logic yourself (AGENTS.md §5).
5. **Review** at the plan's `review` level (workflow/roles/planner.md), by a Reviewer that didn't write the code. For worktree units, each unit was already reviewed during integration (integrate.md); review only the dispatch's app commit with the Hotspots, if any (target `<dispatch sha>^..<dispatch sha>`), then go to Close.
   - Dispatch one Reviewer for the first pass (§1; `skip`: none) with `task: review`, `plan:`, `target: uncommitted`, `level:` the plan's, and `out:` the `## Review` section of the progress note.
   - **Lens check.** If a returned `Lenses:` line shows a lens `not run`, a lens `(read)` on a harness with a skill mechanism, or a fallback whose reason is neither harness.md nor a failed call, dispatch the same Reviewer brief once more at the same setting, adding "lens not run last time: <lens>". This re-run isn't a deep pass and doesn't escalate. If it comes back the same, add the lens to the review's `Not checked:` line and continue.
   - **Deep pass** only when the first pass says `Deep review: yes`, or it ran below strong tier and the diff turns out to change security, auth, data-integrity or concurrency logic, or is large or cross-cutting. (A strong / medium first pass already covers those areas, so for a `review: full` plan only its own `Deep review: yes` escalates.) Record the reason (§1). Dispatch a strong / high Reviewer with the same brief at `level: full`, plus `focus: <reason>`. Never a third pass.
   - Critical and high findings, plus medium findings whose Fix stays inside the plan's `owns:`, go to a fresh Executor for **one** fix round, with `task: fix:` and those rows (including the Fix column). Before dispatching, set those medium rows' Status to `open`, so a resumed session finds the round (recover.md step 2). It runs one rung above the setting that built the code if it holds a critical or high finding, otherwise at the same setting. Then re-run `check`. If the round held a critical or high finding, a Reviewer at the tier that found it checks the fix: the brief of the pass that found them, with `target:` the fix diff and `rows:` every row in the round. For a medium-only round, check the fix diff yourself and set the rows `fixed`, unless it changes logic beyond the lines the rows point to: then a Reviewer at the first pass's setting does the same check at `level: light`. If a critical or high finding is still open, add a remediation plan with Pri `next` (`source: plan NNN review #n`) and mark it `open → plan MMM`. A medium still open stays `open → phase audit`.
   - Other medium and low findings stay `open → phase audit`. They don't hold the plan.
6. **Close.** Turn the remaining proposed entries into real IDs (§5). Fold any remaining slice notes into the plan's progress note, prefixing each review row's number with its slice letter (`A#1`), and delete them (`git --git-dir=.git/workflow rm -f <note>`, after `add` if it was never saved; a plain `rm` prompts). Drop the plan's "In flight" rows. Set every review row in other progress notes that reads `open → plan NNN` for this plan to `fixed (plan NNN)`. Set `status: done` and the `completed:` date, update the index row with the progress note's path, and save `<type>(<scope>): <subject> (plan NNN)` (AGENTS.md §6 Commits). (Worktree units already have their own saves; this one carries only the close bookkeeping, so it is workflow-only.) Push (AGENTS.md §6).
7. **Partial close.** If the remaining tasks depend on an `awaiting-human` question, close the plan with the scope it delivered. Mark those tasks `superseded → plan MMM` and add plan MMM to the index (`source: plan NNN (partial close)`).
8. **Reconcile next.** If anything shipped or written in AGENTS.md now contradicts a resolution, its reconcile plan runs next.

## 3. Phase end
1. Set the phase to `audit` and run workflow/commands/audit.md with scope `phase <n>`.
2. Build the remediation plans it spawns (critical and high first) before starting the next phase.
3. Set the phase to `closed`. Move its `done` and `superseded` plan rows to `workflow/plans/archive.md` and the `resolved` question rows to `workflow/questions/archive.md` (same table header; create the file if missing), so the indexes re-read every session stay short. In static-only mode, add an acceptance row "run check-full" with `Blocking: yes`; Pick won't start the next phase until it passes.
4. After the last phase, run audit with scope `final` and build the plans it spawns. If that audit had a critical or high finding, or a feature marked partial or missing, run it once more (folder `<date>-final-2`) and build what that spawns. Never a third run (the audit folders on disk show how many have run): go to §4.

## 4. Stop conditions
- **Final audit done** (§3 step 4): write `workflow/progress/complete.md` (what was built, how to run it, pending acceptance items, open questions, any audit finding still open, and a pointer to workflow/retro.md "For the workflow"). The project is now in maintenance: new work comes only through `intake` or `change`.
- **Plan closed** (single-agent mode only, §6): report one line; the next `build` takes the next plan.
- **Session budget reached** (only with automatic resume on; see Session budget above): stop only between steps, with indexes and "In flight" consistent and any unit being integrated finished first. Report one line; the loop starts a fresh session.
- **Unknown harness:** harness.md has no section for the harness you run in. Report it and say: "Run `harness` (Follow workflow/commands/harness.md) from this harness, then `build` again." Change nothing else.
- **Integration unavailable:** a phase needs a required integration (harness.md) and its tools are missing. Change nothing else. Report which one and the recovery steps harness.md records for it, then say to run `build` again.
- **Environment broken:** `setup` fails at recover and stack.md has no fix that works. Report the failing line and say to fix the environment and run `build` again. Change nothing else.
- **Missing requirement:** a required skill is unavailable. Report the skill and the harness, and say to install it at user level and run `build` again. Change nothing else.
- **Nothing actionable** (everything left waits on `awaiting-human` questions or blocking acceptance items): summarize what is blocked, then stop.
- **Usage or context running low** (only when the harness shows a limit is near; otherwise the session just ends and recover.md picks up): dispatch no new units (effort may drop on non-critical work in flight, never on high-risk work; §1). Finish or checkpoint the current step (tasks honestly ticked, indexes and "In flight" consistent), integrate any unit that has finished, then stop. Units still running stay in their worktrees, and the next `build` resumes them from disk (recover.md steps 2–3).
Otherwise, never stop to ask.

## 5. Turning proposed entries into real IDs
For each `new-Q`, `new-D` and `new-A` key in a unit's plan or note, in order: take the next free ID of that type, write the question file, decision file or acceptance row from its template, add the index row, and replace the local key with the real ID in the plan or note. Only the Orchestrator does this inside the loop (exceptions: AGENTS.md §5 IDs), and only on the integration branch. An acceptance row gets `Blocking: yes` only for `check-full` in static-only mode or a tier-3 check of an AGENTS.md §4 constraint; otherwise `no`, whatever the proposal says.

## 6. Single-agent mode
Applies when harness.md says this harness has no sub-agents. You play every role in turn (AGENTS.md §5): wherever a command says "dispatch", read that role's file and do the work yourself.
- **One plan per session.** Run recover.md, then take one plan through Pick, Plan, Execute, Verify, Review and Close, always `sequential`. Then stop (§4, "Plan closed"). Finishing work that recover.md resumed counts as the session's plan.
- **Plans:** no brief check. With a small model, keep a plan to about 5 tasks.
- **IDs:** write real IDs directly instead of proposed entries.
- **Skills:** `caveman` throughout; `ponytail` while planning and implementing, off for the review.
- **Review:** a separate pass that follows workflow/roles/reviewer.md strictly. If the harness can clear your context (harness.md, Context reset), clear it after writing the plan and again before the review; disk carries everything over.
- **No Helpers:** read a failing log yourself, the summary and the first failing lines only.
- **No ladder:** you run at the session's setting. Where §1 says to escalate, retry once; a second failure becomes a remediation plan or a question.
- **Audits:** one section per session, in audit.md order; recover.md step 4 resumes at the first missing step.
